# Review: shared-person widget plan (68332e2)

Reviewed on Mac, read-only, against `origin/main` 9761515 (the plan's base) and primary docs fetched 2026-11-01. Every cited line was opened.

## Verdict: ready with changes

The plan is correct on the hard parts (Keychain, Convex HTTP API, Worker/bootstrap name handling, day semantics, Pro-record reuse) but carries machinery the owner's rules forbid, misses the prod cutover, and under-specifies the Keychain write path for fresh installs. Apply the required changes below before implementation starts.

One more verified fact the plan does not use: **unscoped `SecItemCopyMatching`/`SecItemUpdate`/`SecItemDelete` search all of the app's access groups; `SecItemAdd` without a group writes to the app's first group, which is the app ID when there is no `keychain-access-groups` entitlement** (https://developer.apple.com/documentation/security/ksecattraccessgroup, Discussion). Changes 1, 2, and 6 follow from it.

## Required changes

1. **Scope only `SecItemAdd` to the App Group; leave reads, updates, and deletes unscoped.** Plan §2 (line 67) wants the explicit group "for all canonical identity reads/writes/deletes". A scoped read misses an unmigrated legacy item, and an unscoped read already finds the group item (doc above). Minimal change to `SharingKeychainItem` (`SharingSecureStorage.swift:27-38`): optional `accessGroup`, applied only in the add path. The invite item stays private automatically (default = app ID group). Migration in the app: unscoped `SecItemCopyMatching` with `kSecReturnAttributes` + `kSecReturnData`; if `kSecAttrAccessGroup` ≠ the App Group, `SecItemAdd` scoped to the group, read back scoped, `SecItemDelete` scoped to the group string the attributes returned. About 25 lines, idempotent, runs once at launch before any auth. Drop the "conflicting identities / disable widget access / setup error" branch: two distinct items cannot arise because the legacy unscoped `SecItemUpdate` (`SharingSecureStorage.swift:29`) hits the existing item in any group; an unscoped add only happens when no item exists anywhere.
2. **Fresh installs must add the identity into the App Group too.** The plan only migrates legacy items. `SharingIdentityStore.loadOrCreate` → `save` → `SecItemAdd` unscoped lands in the app's private group, so a first-time sharing user on the new build would have a widget that never sees the identity. Fix is the same `accessGroup` on the identity item's add path (change 1); no separate credential store file is needed. `Shared/SharingWidgetCredentials.swift` reduces to the `SharingKeychainItem` + `SharingIdentity` types moved under `Shared/`.
3. **Build-25 upgrade and downgrade statement.** Add to §2: build 25 keeps working after migration and after a TestFlight downgrade, because its unscoped reads find the group item and its unscoped update edits it in place; `SharingKeychainItem.delete()` (unscoped, `SharingSecureStorage.swift:40-45`) removes both copies on profile deletion, which is the desired behavior. No orphaned or duplicated server profile is possible on this path; `loadOrCreate` only creates when no item exists in any group.
4. **One deployment constant, and sequence the feature after the pigeon → puffin cutover.** The plan hardcodes `https://energized-pigeon-822.convex.cloud/api/query` (line 109) and never mentions `tacit-puffin-847`. Move `convexDeploymentURL` and `authBaseURL` from `Features/Sharing/SharingConfiguration.swift:4-5` (app-only, ConvexMobile-adjacent) into `Shared/SharedAppConfiguration.swift` so app and extension read one value. The Worker has a single `CONVEX_BOOTSTRAP_URL` and `JWT_AUDIENCE` (`worker/auth/wrangler.jsonc:23`, `auth.config.ts:5`), so it can serve one deployment at a time; ship order is: deploy the additive backend change to puffin → switch the constant and Worker bootstrap URL → build. The extension's cached JWT record must store the deployment URL it was minted for and be discarded on mismatch, otherwise a token minted for the old audience is replayed after cutover until its 24 h expiry.
5. **Reuse `personDay` with an optional `includeFoods` argument instead of `widgetPersonDay` + `personDayRead.ts` + typed error codes.** `sharing.ts:380-420` already performs every check the plan lists; add `includeFoods: v.optional(v.boolean())` (default true) and skip the `sharedFoodDays` read when false, returning `foods: []`. The return validator (`sharingValidators.ts:50-53`) is unchanged, so build-25 callers are untouched. The "profile-existence oracle" the plan guards against does not exist: missing, deleted, self, stranger, and removed all throw the same `"Relationship unavailable."` (`sharing.ts:391,396`); malformed IDs fail argument validation, which is the same for any ID-typed arg. Display name comes from the people cache, not the query. Extension rule, needing no codes: a decoded `status:"error"` envelope after one token refresh and retry is authoritative (treat as unavailable, purge that person's cache); non-JSON body, transport failure, 429, 5xx are transient (keep last-good). `AUTH_REQUIRED`/`PROFILE_UNAVAILABLE` add a helper, a ConvexError path, and client parsing for a distinction the extension never acts on differently (viewer profile deletion is app-initiated and already purges locally).
6. **JWT cache is extension-private; the app never publishes tokens.** An unscoped add from the extension lands in the extension's own app-ID group, which is all that is needed. This removes the cross-process Keychain write, the "independent writes are safe" reasoning (line 71), and the app-side publish hook. Cost: the extension does one `/v1/token` exchange per 24 h per device, which the Worker already rate-limits per IP (`index.ts:36-50`).
7. **One `generation` UUID replaces control revision + session generation + `NSFileCoordinator`.** Single control file in the App Group (`{version, generation, enabled, defaultProfileId, people:[{id,name}]}`) written only by the app with atomic `Data.write(.atomic)` and `completeUntilFirstUserAuthentication`. The app bumps `generation` on disable, delete, identity replacement, default change, confirmed removal, and app-observed denial, then deletes old cache files best-effort. Extension cache files are named `<generation>-<profileId>-<day>.json`; on read the extension ignores any file whose generation is not the current one. A late extension write with a stale generation is therefore inert, which is the only race the three-layer design was protecting against. Cut "last successful authorization time", the people-cache "authoritative" flag (an empty `people` array after a successful dashboard is authoritative by construction; the app only writes on `receiveDashboard`, `SharingSyncService.swift:268-295`), and the 60-second cross-family reuse (two instances × 48/day is trivial for Convex and the reuse adds a freshness state).
8. **Deep links: one new URL.** Keep `calmacrotracker://sharing/person/<profileId>`. Pro-locked, disabled, no-default, and settings states open the existing `calmacrotracker://sharing` (`AppOpenRequest.swift:30-36`), which lands on the Sharing hub where the Shared Widgets section and `ProLockedRow` live. Cut `sharing/widgets` and `sharing/widgets/upgrade?person=` with purchase-resume routing; that is speculative navigation for a tap that already reaches the paywall in one more tap.
9. **Explicit `nonisolated` on every type the extension shares with App Intents.** Both targets set `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` (`project.pbxproj:505,598,640`). `AppEntity`, `EntityQuery`, `WidgetConfigurationIntent`, and the Codable DTOs must be `Sendable` and callable off the main actor; follow `WidgetAppearanceStorage.swift:3,21,33` and mark them `nonisolated`. The plan mentions this in passing (line 344); make it a completion gate for task 4.
10. **Release sequencing against App Review.** State in §10: do not upload the widget build until 1.0 is approved and change 4's cutover is done; the build must ship pointing at puffin. Backend changes to pigeon while 1.0 is in review are acceptable only when additive and optional (the `includeFoods` arg qualifies). Lock Screen widgets showing another person's health data are allowed; the plan's `.privacySensitive()` and disclosure copy are sufficient, and no new privacy-label category is required (`docs/app-store/privacy-labels.md:11-13` already covers shared nutrition linked to the sharing profile; add the word "goals" to row 11).
11. **E2E matrix: trim to what proves the feature.** Required artifacts: per family (5) the shared-with-goals, not-shared, Pro-locked, and offline-with-last-good states; Home Screen person picker; one Default instance and one explicit instance before and after a default change; one natural extension-originated refresh with request and entry timestamps; cold and warm person deep link; the API negative run output. About 30 artifacts. Fold the raw `/api/query` negative assertions (stranger, unauthenticated, expired JWT, ungranted direction, ended grant, removed, tombstoned, `includeFoods:false` never returns foods) into the existing `convex-backend/scripts/sharingSmoke.ts` next to its current checks rather than a second script. Tinted/clear/vibrant, long and Unicode names, large text, VoiceOver, reduced motion, StandBy, DST, and the midnight rollover move to optional notes; the midnight entry and DST math stay covered by the prewritten isolated clock test. For the offline cell, name the tool: macOS Network Link Conditioner "100% Loss" for the single capture, restored immediately after.

## Security and privacy notes

- Identity migration: with changes 1–3 there is no path that creates a second server profile; the only destructive step is the scoped delete of the legacy copy after a scoped read-back of the group copy succeeds.
- The extension holding `profileSecret` is an accepted trade-off. A Worker-minted read-only token (claim checked in Convex mutations) is the eventual hardening; it is a Worker + Convex change and stays out of scope.
- Cache purge races: handled by generation tagging (change 7). Also delete cache files whose day is not today on every provider run; this bounds disk and removes yesterday as a fallback source.
- Authorization-negative test: keep the raw-transport requirement (same `/api/query` path as the extension, not `ConvexHttpClient`) and assert on the decoded envelope.
- Lock Screen: `.privacySensitive()` on name and nutrition, plus the Sharing Settings disclosure, is the right scope. Default iOS behavior shows accessory widgets while locked; the plan correctly treats that as disclosed behavior, not something to engineer around.

## Open question: temporarily enabling `settings.sharingRequirePro` on energized-pigeon-822

**Recommendation: no, not while pigeon serves the 1.0 build in App Review and TestFlight.** The flag is deployment-global (`proModel.ts:10-12`); flipping it pauses every connection without a server-verified Pro on both ends, including any pair App Review is exercising, and blocks invite creation for build-25 users for the window (`sharing-v2-plan.md:181`; `sharing-v2-backend-validation.md:63-65` already records that pigeon must not be touched for this reason). The widget's paused rendering is a copy branch on the `visibility` value with the same client path as `notShared`; the server decision is already proven deterministically in `convex/_qa/sharing.integration.ts:182-202`. Mark the live paused cell blocked with that test as coverage. Revisit after the puffin cutover, when pigeon becomes a true dev deployment; then a short owner-coordinated flip with Sandbox-verified fixtures is reasonable.

- `SharingLocalStateStore.isDeviceSharingEnabled` is in standard defaults (`SharingLocalStateStore.swift:11-14`); the control file's `enabled` is the extension's only source, as the plan states.
